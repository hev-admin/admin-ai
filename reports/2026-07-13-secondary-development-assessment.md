# 二次开发评估报告（基座扩展性）

> 评审来源：REVIEW.md 2026-07-13 评审项 1。
> 评估口径：**是否易于在此基座上进行扩展开发**——即以 admin-ai 为起手脚手架开发真实业务系统时，新增/改造的成本、风险与保障。
> 评估方法：走查全部四个包（apps/web、apps/server、apps/docs、packages/request）的源码与文档，按「典型二开路径」逐条推演成本；结论均给出代码/文档证据位置。
> 评估基线：M1–M5 全部完成（TASKS.md），commit `8934a81`。

## 一、总体结论

**该项目具备良好的二次开发基座条件，总评 4 / 5。**

核心优势是「约定完备且约定即文档」：后端三层分层有硬边界、新增实体/接口/页面的主路径全程有步骤级文档与可对照范例；架构上刻意收敛的三个耦合面（数据驱动、UI 组件库、请求适配器）都给出了明确的切换成本模型，而不是空承诺。

主要短板集中在两处：**质量保障（零测试设施）**与**生产化能力缺口**（日志、安全加固、部署形态）。二者都是需求文档明示的范围裁剪（REQUIREMENTS §14 非目标），不是设计缺陷，但二开团队必须在业务开发早期自行补齐，本报告给出分级建议。

## 二、分维度评估

### 2.1 架构分层与模块边界（5/5）

**后端**（apps/server/src）：请求路径 `中间件链 → routes → services → repositories` 四段，每层职责在文档与代码注释中均有硬性约定：

- routes 只做「zod 校验 + 权限注解 + 调 service + 包装响应」（`src/routes/users.js` 是标准样板：schema 就近声明、`requirePermission` 先于 `validate`）；
- services 承担跨实体逻辑与完整性校验（「先校验后执行」），关联读取在这层内存拼装，**禁止 import prisma/mongodb 驱动**（apps/docs/guide/backend.md「分层约定」明文）；
- repositories 是唯一接触数据库的层，统一操作集契约（8 个方法 + 平铺 where 语义）写在 `src/repositories/index.js:1-37` 的 JSDoc 里，Prisma / Mongo 两套实现共享同一契约。

这个边界对二开的价值是**决策免除**：新代码往哪放、能 import 什么，不需要讨论。且 `repositories/index.js` 的惰性装配（`DB_DRIVER` 启动时决定、未启用驱动的模块图完全不加载）意味着只用一种库的团队不为另一套实现付运行时成本。

**前端**（apps/web/src）：目录按 api / components(Pro\*) / composables / directives / layouts / locales / router / stores / theme / utils / views 划分，关键约束是「`stores` / `utils` / `router` / `api` 禁止 import UI 库」（UI 依赖只出现在 views / layouts / components），这是 UI 库可切换的结构性保证，也天然避免了状态层与视图层的缠绕。

**共享包**（packages/request）：`createRequest` 工厂 + fetch/axios 双适配器 + `RequestError` 规范化，同构（浏览器/Node），web 与 server 出站请求复用同一包。钩子模型（onRequest / onResponse / onError）足以承载业务拦截语义（`apps/web/src/utils/request.js` 即范例：token 注入、`{code,data,message}` 解包、401 整页跳转、silent 逃逸口）。

### 2.2 典型扩展路径成本走查（5/5）

这是本次评估的核心口径。逐条推演二开最高频的六条路径：

| 扩展路径                      | 步骤（全部有文档）                                                                                                    | 成本评估                                                                                                                                          |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **新增业务实体 + 接口**       | schema.prisma 加模型 → `db:migrate` → prisma/mongo 两套仓储各 1 行工厂登记 → service → route → `routes/index.js` 挂载 | 低。仓储工厂（`repositories/prisma/base.js`）把单实体 CRUD 压缩到一行声明（fuzzyFields / relations 配置）；backend.md「新增接口」有完整 demo 代码 |
| **新增前端页面 + 菜单**       | `views/<模块>/index.vue` → 菜单管理登记（或改 seed）→ 补 zh/en 语言包 → （可选）按钮权限码节点                        | 低。菜单即路由，动态注册自动处理组件名/keep-alive；三个系统管理页面是可复制的 Pro\* 组件范例                                                      |
| **新增语言**                  | 拷贝语言包目录逐文件翻译 → locales/index.js 注册 → naive.js 补组件库映射                                              | 低，frontend.md 给了逐步清单与键集校验方法                                                                                                        |
| **SQLite → PostgreSQL/MySQL** | 改 provider → 换 driver adapter → 换连接串 → 重建 migrations → 回归                                                   | 中。是文档化流程而非配置开关（Prisma 迁移 SQL 绑定方言，这是 Prisma 的固有约束不是本项目缺陷）；schema 层「不使用 @db.\* 注解」约定保证模型零改动 |
| **启用 MongoDB**              | `.env` 改 `DB_DRIVER=mongo` + 跑一次 mongo 种子                                                                       | 极低。routes/services 零改动，M4 已做过三账号全流程回归                                                                                           |
| **切换 UI 组件库**            | 换 resolver → 重写 useFeedback / Pro\* 内部 / theme 映射 / locale 映射 → 按 `<N` 前缀清单替换展示组件                 | 中。定位是「设计时受控切换」，frontend.md 给出 7 个适配点的精确清单，成本可预估、不发散                                                           |

**共同特征**：每条路径都有（a）收敛的改动面、（b）步骤级文档、（c）仓库内可对照的已实现范例。这是「模板型项目」最重要的质量指标，本项目做得扎实。

### 2.3 工程化与规范（4/5）

- **单配置 ESLint**（根 `eslint.config.js`，@antfu/eslint-config 承担 lint + 格式化，无 Prettier）：二开子包零配置继承，auto-import 全局名经 `.eslintrc-auto-import.json` 打通，不会出现「auto-import 变量被 lint 报 undef」的常见坑；
- **纯 ESM + 无构建后端**：`node --watch` 直跑源码，dev 与 prod 运行同一份代码（REVIEW.md 2026-07-10 已评审确认此选型），排障心智成本低；
- **pnpm 原生 workspace**（不引 Turborepo/Nx）：4 个包的规模下正确的选择；`pnpm-workspace.yaml` 已沉淀弱网参数与 pnpm 11 `allowBuilds` 构建授权，环境复刻性好；
- 扣 1 分的原因：**无 CI 配置**（无 .github/workflows），lint 与后续测试没有强制门禁，二开团队多人协作时约定容易漂移。建议最小 CI：`pnpm install --frozen-lockfile && pnpm lint`（后续追加测试）。

### 2.4 文档与知识沉淀（5/5）

- 文档站五篇（getting-started / architecture / frontend / backend / api）**明确面向二次开发者写作**——frontend.md 开篇即「面向在本模板上做二次开发的场景」，backend.md 同；文档不只写「怎么做」还写「行为口径」（如 JWT 权限变更需重登、改密后旧 token 有效、跨库模糊搜索大小写差异），这些恰是二开最容易踩的暗坑；
- REQUIREMENTS.md 保留全部选型理由与**非目标清单**（§14），TASKS.md 保留每个里程碑的决策点与完成记录，REVIEW.md 保留评审分歧与结论——二开团队能追溯「为什么是现在这样」，避免无谓的重新发明；
- 文档内的扩展方向预留（如接口 message 国际化的两条升级路线、权限即时生效的改造点）等于提前画好了二开的施工图。

### 2.5 质量保障（2/5）—— 最大短板

**仓库内没有任何测试**（无测试框架、无测试文件；REQUIREMENTS §14 明示「不做单元测试 / E2E，预留后续引入空间」）。对二开的具体影响：

1. **repository 双驱动一致性无回归网**：契约靠文档与人工对齐，二开新增实体要在两套实现登记并保持行为一致（where 语义、id 互转、关联清理），没有契约测试兜底，漂移只能靠手工发现；
2. **RBAC 链路回归靠手工**：文档中多处「回归验证：三账号全流程」均为人工步骤，二开改动鉴权/权限相关代码时成本高且易漏；
3. 架构本身**对测试友好**（`createApp()` 工厂注释明言「便于后续用 app.request() 做无服务测试」；service 纯函数、repository 可替换），补测试的技术阻力小——缺的是设施与用例，不是可测性。

### 2.6 生产就绪度（3/5）

模板完成度对「demo 到开发」很高，但「开发到生产」存在能力缺口，二开团队需按业务逐项补齐：

| 缺口                                  | 现状                                                          | 二开影响                                                                                        |
| ------------------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 结构化日志                            | `hono/logger` 控制台明文                                      | 无请求 id、无级别、不可采集；生产排障困难                                                       |
| 登录安全                              | 无验证码 / 限流 / 锁定；token 默认 7 天长效、无刷新与吊销机制 | 面向公网必须补（文档已如实声明口径）                                                            |
| 事务                                  | repository 契约不承诺跨实体事务，service「先校验后执行」      | 强一致业务（资金/库存类）需自行下沉事务，且 Mongo 侧事务需 replica set                          |
| 复杂查询                              | 平铺 where 只支持等值/in/模糊/关联包含，无范围、OR、聚合      | 报表/时间区间筛选类需求要么扩契约（两套实现同步动），要么绕过契约单独实现（打破抽象需明确规约） |
| 文件上传 / 缓存 / 任务队列 / 审计日志 | 无                                                            | 常见后台能力，按业务补                                                                          |
| 部署                                  | 生产 = 目标机 pnpm install + 直跑源码                         | 无容器化（见同日 Docker 专项报告）                                                              |
| API 文档                              | 手写 markdown（apps/docs/api/index.md）                       | 二开新增接口需手工同步，易漂移                                                                  |

### 2.7 类型安全（3/5）

全仓库不引 TypeScript 是既有约定（REQUIREMENTS §14），评估尊重该约定。实际影响：关键契约（repository 操作集、createRequest 选项）已有质量较高的 JSDoc，IDE 有基本提示；但跨层重构（如改 service 函数签名）无静态检查，团队规模大时风险上升。可在不违反约定的前提下渐进增强（见建议 P3）。

## 三、二开风险与注意点清单

以下是走查中识别的、文档已声明但二开时仍高概率踩到的点，建议纳入团队入职清单：

1. **权限变更生效时机**：`requirePermission` 读 JWT 载荷不查库，改角色权限后须重新登录才对 server 生效（super 短路不受影响）。误判为 bug 的概率高。
2. **菜单图标双处同步**：图标类名存数据库、运行时拼接，UnoCSS 静态扫描不可达——新图标必须同步登记 `apps/web/uno.config.js` 的 safelist，否则静默不渲染。
3. **语言包必须平铺 key**：`'menu.system'` 与 `'menu.system.users'` 需共存，写成嵌套对象会静默查不到。
4. **Mongo 种子需补齐可空字段**：文档缺键会在序列化时丢字段，导致两库返回形态不一致。
5. **删除自身防护语义**：批量删除静默过滤当前登录账号（`services/users.js`），二开仿写其它实体的批量删除时注意对齐该口径。
6. **auth 白名单是精确路径匹配**（`middlewares/auth.js` 的 `Set`）：新增免登录接口须显式登记，带路径参数的公开接口需改为前缀匹配。

## 四、改进建议（按优先级）

- **P0 引入最小测试设施**：vitest + Hono `app.request()` 集成测试。最先覆盖两块——(a) repository 契约测试套件（同一份用例跑 prisma 与 mongo 两套实现，锁死双驱动一致性）；(b) RBAC 链路（三账号 × 关键接口的 401/403/200 矩阵）。这是把「二开回归成本」从手工降为自动的最高杠杆点，且架构已预留可测性，预估改造无侵入。
- **P1 容器化部署**：见同日《Docker 整体打包改进方案报告》（reports/2026-07-13-docker-packaging.md）。
- **P1 API 文档自动化**：zod schema 已就近声明，评估引入 `@hono/zod-openapi`（或 hono-openapi）从现有 schema 生成 OpenAPI 文档，替代手写 api/index.md 的同步负担。注意需评估路由声明风格的改写成本，可先在新模块试点。
- **P2 最小 CI**：GitHub Actions 单 job（install --frozen-lockfile → lint → 后续追加 test），防约定漂移。
- **P2 结构化日志**：以 pino（或同类）替换 hono/logger，注入请求 id；保持中间件层替换、业务码零改动。
- **P2 登录防护**：登录接口限流（hono 生态中间件或自实现滑窗）、可选验证码位；评估 token 短效 + refresh 方案（文档已预留「token 版本号 / 黑名单」两条路线）。
- **P3 图标 safelist 自动化**：从 `seed/data.js` 菜单树提取图标类名生成 safelist 片段的一次性脚本，消除双处同步。
- **P3 渐进类型检查**：不引 TS 语法，仅对 `packages/request` 与 `repositories` 契约层启用 `// @ts-check` + JSDoc typedef，收益集中在最需要契约稳定的两处。

## 五、结论

以「起手脚手架」的定位衡量，admin-ai 的**可扩展性设计是自觉且落地的**：三个可切换耦合面（数据驱动 / UI 库 / 请求适配器）全部给出了诚实的成本模型，高频二开路径全部文档化且有范例，决策记录完整可追溯。**建议作为基座采用。**

采用时的前置动作按优先级执行第四节建议，其中 P0（测试设施）应在业务代码大量进入之前完成——这是当前基座唯一会随二开规模放大的结构性风险。
